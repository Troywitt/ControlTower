# Security boundary — review version 0.4

## Dashboard

The active executable is `ControlTowerLocal`. It is ad-hoc signed with hardened runtime and App Sandbox, and only `files.user-selected.read-only`. **No network-client entitlement**, updater, shell/process launch, credential entry, Keychain adapter, browser-cookie or provider-auth-file discovery. The old direct-token core is isolated in a test-only target and is not a product dependency. `KeychainVault.swift` is explicitly excluded from the executable.

Users select a dedicated quota-feed folder, granting the dashboard read access to that folder for this launch. It reads fixed `claude.json`/`codex.json`/`gemini.json`/`grok.json` names every five seconds while enabled. Disconnect ends reads and the security scope. No persistent bookmarks or startup reconnection. Folder-level grant is necessary because atomic replacement changes file identity; select only the dedicated quota folder, never a credential/state/project folder. Files must be regular, non-symlink, bounded; feed JSON has a strict field/provider/window allowlist and rejects booleans, nonfinite values, invalid percentages, future timestamps and unknown fields. Missing/error data removes displayed success; observations older than five minutes are marked stale. Local same-user tampering cannot be prevented by this JSON boundary; feeds are not cryptographically authenticated. StatusLine observation time is not a guaranteed network-fetch time.

## Claude bridge

`Bridges/prepare_claude.py` generates review/rollback patches; it never edits `.claude/`. It reads the user-selected settings file locally but only retains statusLine. Existing command/options are preserved; unknown formats, recursive wrapping and overwrite attempts fail. Review directory must be private. The statusLine bridge receives official stdin, bounds it, selects only quota percentages/reset times, and publishes using a 0600 temporary file + atomic rename. It never saves/logs raw stdin or transcript/path/session fields. If an existing command is preserved, raw input is passed **in memory** to that same trusted command, as Claude already did; its preexisting privileges/behavior are not sandboxed or audited by this fork. Prior command output goes directly to the terminal, stderr is suppressed, and a timeout bounds waiting. No provider credentials are used by the bridge.

## Codex adapter

`Bridges/codex_quota.py` is **user-started outside the app sandbox** in a private terminal. It verifies the explicit executable's SHA-256 and Apple signing requirement (identifier `codex`, team `2DC432GLL2`) before starting the unmodified provider executable. It preserves the real OS HOME (resolved from the current UID, not inherited environment) so macOS can locate the default Keychain. CODEX_HOME stays at the exact dedicated private profile; the empty working directory is a separate Git repository bounding parent discovery. A fresh allowlisted environment excludes inherited provider keys, proxies and endpoints. First-use state must be empty; a marker guards accidental selection of an unrelated state folder. CODEX_HOME and credential storage are configured for the child only; existing user config is not modified or inspected. System/MDM policy still applies.

The normal `$HOME/.codex/config.toml` is excluded by the explicit CODEX_HOME, confirmed with an invalid synthetic default-config fixture against the pinned binary. Child flags disable hooks, plugins, remote plugins, apps, workspace dependencies, shell snapshots/tools, memories and external memory imports; host-skill skipping is requested. Known machine-policy paths cause a stop for review before these overrides; managed policy is not ignored or rewritten. An explicit `skills/list` request can still discover host skills even with the skip flag: this flag is not a filesystem firewall. The production method allowlist therefore excludes skill/hook/plugin/config listing, threads and turns. The provider remains an ordinary user process, not a sandboxed guarantee of zero filesystem access. Only Keychain path/status metadata was used to verify lookup; no items were read or default/search-list settings changed.

The Start launcher now runs official `login --device-auth` first, with inherited user-terminal stdin/stdout/stderr and no capture. The provider handles enrollment end-to-end; the wrapper waits only for exit status. Only exit0 starts a new official app-server for initialize + quota-read. Login and quota processes share the same verified executable, real OS HOME plus private CODEX_HOME, minimal environment and keyring-only configuration. The feed lock spans the handoff; failure/cancellation stops the sequence without automatic login retries. Ctrl+C terminates the owned provider process group with bounded cleanup; overall enrollment wait is660seconds. Resume skips enrollment. Provider-managed login logs/storage are not read by the wrapper; official-client logging is outside its quota-only output boundary.

The older diagnostic app-server login path is retained but is not selected by the Start launcher. Stdio has fixed RPCs: initialize, device-login start/cancel, quota read. No general RPC/UI command surface; no turns, tools, model prompts, credits/reset, email or generic account operations. Incoming server requests fail closed. Device destination is fixed to `https://auth.openai.com/codex/device`; code stays in the user's terminal and is never published. OAuth/session tokens and credential files are never requested/read by wrapper or dashboard. Official Codex owns its authentication, Keychain storage and refresh. Explicit `keyring` requests no plaintext fallback; real behavior and rebuild/persistence must still be live-tested. The official binary may possess account access broader than quota reads; our method allowlist is not OS isolation of that binary.

The helper writes only normalized quota fields, uses bounded framed input/timeouts, never logs provider bodies or errors, suppresses child stderr, and terminates its process group on exit. Refresh is user-owned; failure exits without fallback/retry. The device flow needs no wrapper network listener or app entitlement expansion. The child still has normal user-process network access: **old URLSession host restrictions do not apply to it**. Disconnecting the dashboard does not kill this separate helper; quit it in Terminal. Saved provider login remains provider-managed. No global certificate/network/security setting is changed.

## Gemini and residual limits

The Gemini adapter launches the unmodified official npm CLI 0.60.0 in a private Terminal with a new provider home. The user owns trust prompts, Google sign-in and `/model` commands. The adapter sends no generated keystrokes. Official code manages credentials; no existing auth files are copied/read by the adapter. Child telemetry, usage statistics and automatic updates are disabled. Dedicated empty system/default settings and disabled parent-memory discovery prevent loading unrelated configuration; an existing machine-level Gemini policy stops setup for review rather than being bypassed. Node and installed runtime trees are hash-pinned.

A bounded in-memory terminal screen is parsed only when the complete model dialog and fixed tier rows are present. Unknown labels, malformed numbers, partial rows and duplicate tiers fail closed. Only Pro/Flash/Flash Lite labels, integer used percentages and approximate reset epochs leave the terminal. Raw terminal output, input and account identity are never logged. Output is atomic and owner-only; a single-writer lock prevents competing helpers. An open dialog publishes once, so idle redraws do not make an observation fresh. Ctrl+] or client exit stops the child process group and publishes unavailable. The parser is version-specific, best-effort UI extraction, not a supported quota API. Resets are estimated from the CLI's minute-rounded duration.

No headless `/stats`, OAuth client-key copying, credential extraction, automatic trust acceptance or custom internal API request is shipped. The separate official client has ordinary user-process privileges. Its authentication storage is provider-managed and is not claimed to be Keychain-only. Runtime account acceptance is still pending.

## Grok

The pinned, signature-verified official Grok 1.0.40 CLI runs with its own provider home. The same bounded terminal loop used for Gemini accepts only the SuperGrok weekly usage display. No generated input, model requests, token extraction or API billing import is used. The user owns all trust/sign-in actions. Each startup disables updates/leader reuse/telemetry and cross-tool configuration discovery, then runs a bounded official configuration inspection; external extensions or instructions stop startup. Existing machine policy stops setup rather than being bypassed. Inspection output is never saved or printed.

Only the fixed Weekly label, integer usage percentage and unambiguous estimated reset are published. Date timezone/year inference is limited to an upcoming weekly window; ambiguous daylight-saving times omit the reset. Official client values can be cached, and public source does not exactly match the binary commit. Real authenticated screen compatibility is still pending. Grok's credential storage is provider-managed, not claimed Keychain-only. The provider executable has ordinary user privileges; private configuration is not an OS sandbox.

Ad-hoc signing is not notarization or identity continuity. A compromised user account, app, helper, official provider binary or OS can defeat these boundaries. Signature/hash checks reduce substitution risk but do not make same-user filesystem changes impossible. No absolute security or provider-terms guarantee is claimed. Synthetic tests verify our boundaries, not provider reliability or real account authentication. See [PROVIDER-SETUP.md](docs/PROVIDER-SETUP.md) and [HANDOFF.md](docs/HANDOFF.md) for acceptance gaps.
